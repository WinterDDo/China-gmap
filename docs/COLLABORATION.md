# 多会话协作

同一时间可能有好几个 Claude 会话在改这个项目，每个云端会话有自己的 `claude/…` 分支。这份文件是规则全文，
`CLAUDE.md` 里是摘要。现状不用记：开工时的看板（`tools/board.py`）会自动列出来。

## 为什么要有这些规矩

2026-11-27 一天之内实际发生的：

- GitHub 的默认分支是某个会话的工作分支。新会话从它起步，别的会话加的规则、钩子和 skill 传不过去。
- 早上一个会话修了一处解析错误（泸州 2020 年把「家庭医生签约人数」当成了常住人口），12 小时没并进任何主线，差点丢掉。
- 两个会话都把自己的设计定稿叫 5.8，其中一个是已经撤回的 3D 试验。
- 一个会话改了原型数据的口径（人均生产总值改用公报原文的数），另一个会话的检查规则还按旧口径写。合到一起时，测试马上变红。

加盟商项目的教训：手工维护的「谁在做什么」登记表，81% 的合并都要改它，18 行里 17 行已经过期。
靠散文的协作规则会腐烂，所以这里的现状全部从 git 推出来（看板），该拦的由钩子拦。

## 主线

- 主线是 `main`，GitHub 的默认分支也应该是它：新会话从主线起步，才会自动带上 `CLAUDE.md`、钩子和 skill。
  （`main` 建立之前，看板把 GitHub 默认分支当作主线，并在第一行提示。）
- 每个会话只改自己的 `claude/` 分支。不推别的会话的分支，不 force-push，不改写已经推送的提交。

## 开工

1. 看看板：开工时自动显示，也可以手动跑 `python3 tools/board.py`。
2. 主线上有你还没合并的提交：先合并主线，再动手。
3. 先推一次自己的分支。推了就算认领，别的会话的看板上就能看到你。不另外登记。
4. 看板点名「你也改了」某些文件：先把对方的分支并进来，再继续改这些文件。对方在改热点文件：换个活，或者等它并进主线。

## 热点文件

| 文件 | 为什么容易冲突 | 怎么办 |
|---|---|---|
| `explorations/design-freeze/index.html` | 整个原型在一个文件里 | 同一时间只让一个会话改它 |
| `explorations/design-freeze/data/cities.json` | 整个文件只有一行，冲突没法手工合 | 冲突时用同目录的生成脚本重新生成，不手工拼 |
| `STATUS.md` | 每个会话都要更新 | 并进主线前最后一步再改：先合并主线，再加自己的几行 |
| `pipeline/check.py` 里的上限 | 两边可能同时调低 | 冲突时取较小的那个数 |
| `CLAUDE.md` | 规则本身 | 改规则单独提交，提交信息写明改了哪条 |
| `pipeline/parse/bulletin.py` | 改动影响全部数字 | 改完跑 `python3 -m pipeline check` |

## 版本号

设计定稿的版本号用看板给出的「新一版用 X.Y」。撤回过的版本号不再用。两个会话撞了号，后并进主线的那个改号。

## 并进主线

1. 先合并最新主线：`git fetch origin` 之后 `git merge origin/main`。用普通合并：不压扁（squash），不变基改写历史。
   看板靠「是不是祖先提交」判断一个分支有没有并进来，压扁合并会让它失效。
2. 冲突按上面的表处理。处理完测试必须全绿：推送时钩子会再跑一遍，不绿推不上去。
   各自都绿的两个分支，合起来可能是红的。
3. 更新 `STATUS.md`。
4. 推送自己的分支，再把它并进 `main`。并进 `main` 的方式由用户定，定下来之前先问。
5. 看板点名「两天以上没并进主线」的分支：把它并进来，或者问用户还要不要。

## 不做的事

- 不建手工登记表，也不在任何文件里写「谁在做什么」。
- 不压扁合并。
- 不替别的会话改它的分支。需要它做什么，告诉用户；用户同意后，才可以给那个会话发消息。
